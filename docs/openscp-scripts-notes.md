# OpenSCP: заметки по scripts.rul и API.log

Подготовлено 2026-09-22 для следующей сессии. Статический разбор; запуск игры и проверка поведения в бою не выполнялись. Игровые файлы не изменены.

Источники: `bin/standard/OpenSCP/Ruleset/scripts.rul`, соседний `API.log`, `src/Engine/Script.{h,cpp}`, `src/Engine/ScriptBind.h`, `src/Mod/ModScript.h`, привязки и вызовы в `src/Savegame/BattleUnit.cpp` и `SavedBattleGame.cpp`.

## Устройство файла

В scripts.rul 59 активных обработчиков в 17 событиях. Внешний формат — YAML:

- `extraStrings`: английские и русские сообщения, названия частей брони и навыков.
- `extended.tags`: объявления типизированных тегов объектов.
- `extended.scripts`: глобальные обработчики событий, каждый с `offset` и `code: |`.
- `skills`: пять навыков выбора головы, корпуса, рук, ног и сброса прицеливания; SKILL_ID 10–14.

Начальный пример смены пола закомментирован. Экспериментальные механики внутри extended.scripts, напротив, активны при выполнении их условий.

## Язык

Собственный типизированный язык движка: парсер переводит команды во внутреннее представление, исполняемое ScriptWorker. YAML лишь хранит текст программы.

```text
var int amount;                    # инициализируется нулём
var int chance 25;
var text label "example";
var ptr RuleArmor armor;
var ptre GeoscapeSoldier soldier;

unit.getRuleArmor armor;
armor.getTag amount Tag.ARMOR_LIVING_FIRE;
if and gt amount 0 eq side FACTION_HOSTILE;
  unit.setFire 800;
else eq amount 0;
  debug_log "No living fire" unit;
else;
  debug_log "Other value" amount;
end;
return;
```

Пример тела для newTurnUnit: доступные имена всегда определяются событием.

- Команды заканчиваются `;`, аргументы разделяются пробелами. `#` начинает комментарий. Отступы обязательны для YAML, блоки языка закрываются `end;`.
- `ptr` — указатель с доступом к объекту для чтения, `ptre` — с разрешением изменения. `var` разрешает изменение самой переменной; это отдельное свойство.
- `set x y`, `add x y`, `sub x y`, `mul x y`, `div x y` изменяют первый аргумент. Арифметика int целочисленная. `muldiv x a b` вычисляет `(x*a)/b`; `limit`, `limit_lower`, `limit_upper` ограничивают значение.
- Сравнения: `eq`, `neq`, `lt`, `le`, `gt`, `ge`. `and`/`or` соединяют последовательность простых сравнений; произвольные вложенные логические выражения следует раскладывать на блоки if. Даже `else or eq part 2;` допустимо: один предикат после or парсер принимает.
- Вызовы вида `unit.getHealth value;` записывают результат в аргумент. В API скрытый здесь первый аргумент — сам объект unit. Порядок остальных аргументов нужно читать по сигнатуре, а не угадывать по имени.
- Цепочки вроде `unit.Stats.getHealth value;` и `unit.getPosition.getZ z;` предусмотрены привязками.
- Парсер также поддерживает `const`, `begin`, `loop`, `break`, `continue`. Простейший цикл: `loop var i 10; ... end;`; есть обход API-списков через `.list`.
- Локальные переменные не служат хранилищем между вызовами. Для состояния механик используются теги.

## Порядок обработчиков и возврат

Глобальные обработчики сортируются по offset. Отрицательные выполняются перед локальным скриптом правила, положительные — после. В данном файле все offset положительные. Ноль зарезервирован; модуль offset должен быть меньше 100. Реализация масштабирует число на 100 и переводит в int, поэтому дробные значения имеют ограниченную точность.

Расположение блока в YAML не задаёт приоритет: например, hitUnit с offset 1 записан после offset 99, но исполняется раньше. Одинаковые offset лучше не использовать для зависимых обработчиков: сортировка не гарантирует стабильный порядок равных элементов.

`return` завершает текущий обработчик; последующие обработчики события продолжают выполняться. Число и порядок возвращаемых значений задаются контрактом события:

| Событие | Возврат |
|---|---|
| hitUnit, hitUnitAmmo | `return power part side;` |
| visibilityUnit | `return current_visibility visibility_mode;` |
| selectUnitSprite, selectItemSprite | `return sprite_index;` |
| recolorUnitSprite, recolorItemSprite | `return new_pixel;` |
| accuracy/melee/throwMultiplierBonusStats | `return bonus;` |
| damageUnit | `return;`, изменение выходных `to_*` непосредственно |
| skillUseUnit | `return;`, выходы continue_action и spend_tu изменяются непосредственно |

В damageUnit доступны девять изменяемых выходов: to_health, to_armor, to_stun, to_time, to_energy, to_morale, to_wound, to_transform, to_mana. Пустой return здесь не отменяет внесённые изменения.

## Как читать API.log

Снимок от 12 октября 2025 года: 60 разделов событий и 743 уникальные строки сигнатур операций (включая перегрузки). Это не 743 независимых метода. Дата не доказывает несовместимость, но новые возможности текущего движка надо сверять с исходниками.

Каждый раздел содержит имя события и группу, наличие глобальных обработчиков, иногда стандартную реализацию, выходные значения, доступные переменные/константы и операции. Операции повторяются между разделами; доступность и права указателей надо проверять именно в нужном событии.

Например, `[ptr BattleUnit] [var int]` у getter означает объект для чтения и изменяемую переменную результата. `[ptre BattleUnit] [int]` у setter требует права менять объект. Несколько сигнатур одного имени — перегрузки.

Основные объекты: BattleUnit, BattleItem, BattleGame, GeoscapeSoldier, RuleArmor, RuleItem, RuleSkill, RuleMod, Tile. `battle_game` связан с SavedBattleGame в C++, а `rules` предоставляет доступ к правилам.

Теги различаются по владельцу. BattleUnit.getTag поддерживает также чтение тегов RuleArmor: `unit.getTag victim Tag.UNIT_VICTIM_TYPE;` корректно, хотя тег объявлен у RuleArmor. Это подтверждается отдельной OnlyGet-привязкой брони в BattleUnit.cpp. Нельзя считать всякое такое чтение ошибкой типа. Для отсутствующего значения базовое хранилище возвращает 0; стандартная привязка getTag при null-объекте также возвращает 0. Поведение других методов при null нужно проверять отдельно.

`battle_game.randomRange result min max` использует RNG движка; если max < min или нет объекта игры, возвращает 0. Поэтому некорректный диапазон способен тихо изменить механику, без падения.

| Владение оружием | hitUnit 66 накапливает GeoscapeSoldier.EXP_WITH_TYPE* и уровни; damageUnit 10 использует уровень для критического попадания |

| Прочее | невидимость, утопление на тайле 242, экспериментальные превращения, повторное открытие ран, гибель обречённых после миссии |

В BattleUnit::damage сначала вызываются hitUnitAmmo и hitUnit, затем вычисляются компоненты повреждения, вызываются damageUnitAmmo и damageUnit, после чего движок применяет итоговые компоненты. damageUnit работает до применения итогового урона: прямое изменение HP или брони здесь взаимодействует с последующим штатным вычитанием.

Особая семантика OpenSCP: frontArmor = голова, rearArmor = корпус, right = правая рука, left = левая рука, under = ноги. Ноги дополнительно имеют отдельные теги брони. `part` и `side` — разные индексы; например, корпус part=1 переходит в side=3. В newTurnUnit имя side, напротив, обозначает сторону хода. Контекст события принципиален.

## Наблюдения для следующей работы

Подтверждённые чтением кода, но ещё не проверенные в игровом сценарии:

1. **Вероятность критического попадания** — scripts.rul:1870–1885. RNG из 0..99 складывается с criticalChance, затем проверяется `ge RNG 10`. При исходном criticalChance 5..10 условие проходит в среднем в 97,5% случаев, при уровнях с минимумом 15 — всегда (при to_health > 0 и прохождении ранних условий). Это сильно отличается от ожидаемых 5–10%, 15–20% и т. п. Дополнительный glancing_check влияет на поднятие урона до weaponPower, но не отменяет последующее удвоение.
2. **HMG** — hitUnit 66 ведёт опыт типа 12, а damageUnit 10 выбирает уровень только для типов 1–11. Для HMG expLevel остаётся нулевым. Типы 13–14 присутствуют в сообщениях, но соответствующих счётчиков в этом файле нет.
3. **Проверка drawing routine до чтения** — selectUnitSprite offset 4, около строки 2705: `if eq routine 4` выполняется до getDrawingRoutine. var int routine очищается в 0, поэтому этот защитный блок не срабатывает.
4. **Малый урон и RNG** — damageUnit offset 30: при to_health=1 после div damage 2 получается диапазон randomRange 1 0. Текущая привязка возвращает 0. Нужно решить, соответствует ли это желаемому порогу травмы.
5. **Слепота от flashbang** — ветка damageUnit 1 устанавливает UNIT_EYELESS, но сама не устанавливает SOLDIER_EYELESS. Ветка попадания в голову в damageUnit 15 устанавливает оба тега. Постоянство слепоты между миссиями требует отдельной проверки по всем файлам мода.
6. **Броня ног** — комментарий hitUnit 99 описывает среднее двух значений, но код усреднения в damageUnit 15 закомментирован. Текущую защиту каждой ноги следует проверять с учётом места вычисления поглощения брони в C++.
7. **Сообщения** — в локализациях есть STR_PROFICIENT_MESSAGE_TYPE10_EVEL2/3 вместо LEVEL2/3, тогда как вызовы на строках 1056 и 1060 используют LEVEL2/3. Проверить, нет ли недостающих ключей в других файлах локализации.
8. **Сообщение о полном снятии шока** — healUnit суммирует counter_shock только для тех частей, которым удалось снизить шок. Части выше порога лечения не входят в эту сумму; сообщение о полном снятии может не отражать оставшийся шок.

Перед правкой конкретной механики: проверить контракт события, порядок offset, владельцев и срок жизни тегов, граничные значения RNG/деления и взаимодействие с локальными скриптами правил. Затем проверить поведение в бою; текущие заметки не являются отчётом об успешном запуске или полной проверке мода.

## Дополнение: AllPeopleDifferent.rul, Armors.rul, items.rul, SCPs.rul

Изучены все явные блоки scripts в четырёх файлах. В Armors.rul — 3 локальных обработчика, в items.rul — 9, в SCPs.rul — 2. AllPeopleDifferent.rul содержит один **глобальный** обработчик extended.scripts.createUnit, а не локальный. Числа относятся к определениям текста; наследование расширяет круг правил, использующих их.

### Локальный скрипт, стандартная реализация и наследование

Локальный блок находится внутри конкретного правила брони или предмета:

```yaml
armors:
  - type: EXAMPLE_ARMOR
    scripts:
      selectUnitSprite: |
        add sprite_index sprite_offset;
        return sprite_index;
```

Здесь нет списка offset/code. Для события данного правила задаётся одно локальное тело. Оно **заменяет стандартную реализацию**, а не добавляется после неё. Для selectUnitSprite/selectItemSprite стандартная реализация как раз `add sprite_index sprite_offset; return sprite_index;`. Поэтому отсутствие прибавления sprite_offset в собственном скрипте — значимое решение, которое надо проверять по месту вызова и раскладке графики.

Armor::load и RuleItem::load сначала загружают refNode, затем дочерние поля. ScriptParserBase::parseNode заменяет тело при наличии соответствующего ключа события; отсутствие ключа сохраняет уже загруженный обработчик. Локальный return не выключает глобальные события. Последовательность: отрицательные глобальные offset → локальный/унаследованный/стандартный скрипт → положительные глобальные offset.

### AllPeopleDifferent.rul: создание индивидуальных характеристик

`createUnit`, offset 1, строки 7–348. Условия: текущая фракция не игрок (`faction != 0`, то есть также нейтралы), тег брони UNIT_FIXED_STATS равен 0. Любое ненулевое значение тега отключает рандомизацию.

| Сложность | Диапазон множителя характеристики |
|---|---|
| 0 | 50–120% |
| 1 | 60–130% |
| 2 | 70–130% |
| 3 | 70–140% |
| 4 | 80–150% |

Для каждой характеристики бросок отдельный: TU, stamina, health, manaPool, strength, reactions, firing, throwing, melee, psiStrength, а также ненулевой psiSkill. TU/energy/health/mana как текущие ресурсы устанавливаются вслед за соответствующими характеристиками. Bravery меняется отдельно: бросок 0..5 даёт обычно −20/−10/0/0/+10/+20; для исходных 90 и 100 есть специальные ветки, 110 остаётся неизменным. Комментарий об исключении 90 и 100 не описывает весь код: следующие ветки их всё-таки меняют.

В конце файла UNIT_FIXED_STATS=1 назначается STR_SCP_529_ARMOR_UC и STR_DUMMY_ARMOR_UC. Это дополнительные определения уже существующих правил, а не локальные скрипты.

Связь со scripts.rul: offset 1 выполняется раньше createUnit 12. Следовательно, UNIT_ORIGINAL_TU/HEALTH/STAMINA сохраняют уже рандомизированные величины; последующие шок и травмы опираются на индивидуальную исходную характеристику. Предопределённые ранения createUnit 21 также применяются позже. Эти выводы относятся к совместной загрузке файлов.

### Armors.rul: предупреждение и FPV-анимация

| Правило | Строка scripts | Событие и действие |
|---|---:|---|
| STR_DUMMY_ARMOR_UC | 2978 | newTurnUnit: при UNIT_VICTIM_TYPE=3 и HP ≤ 6 выводит STR_RESPONDERS_CLOSE |
| STR_FPV_BLUE_ARMOR_UC, якорь STR_FPV_ARMOR_TEMPLATE | 3066 | selectUnitSprite: анимация неподвижного дрона |
| STR_FPV_TEMPLATE_ARMOR_UC | 3159 | selectUnitSprite: та же формула анимации, отдельное определение |

Для неподвижного и не падающего юнита вычисляется фаза `((id*11)%8 + anim_frame)%8`, затем итоговый индекс `8*sprite_offset + 8 + фаза`. При движении или падении выполняется обычное `sprite_index += sprite_offset`. Оба правила используют drawingRoutine=4 и constantAnimation=true.

BLACK, BROWN, RED, ORANGE и GREEN FPV-брони наследуют STR_FPV_ARMOR_TEMPLATE через refNode (строки 3180, 3215, 3250, 3285, 3319), поэтому получают и анимацию BLUE, хотя собственных блоков scripts не имеют. Не путать этот YAML-якорь с отдельным типом STR_FPV_TEMPLATE_ARMOR_UC.

Теги ARMOR_SPECIAL_ANATOMY=1 и SA_ONLY_TORSO=1 направляют попадания в корпус через глобальный hitUnit 77. Локальная анимация не отменяет глобальные selectUnitSprite 4/5/6: они получают её результат и могут дополнительно менять индекс при шоке, прицеливании или падении.

Для DUMMY глобальный createUnit 21 задаёт раны, а локальный newTurnUnit следит за падением HP. В предупреждении нет проверки стороны хода и флага «уже показано»; при повторных подходящих вызовах сообщение повторяется. Условие также допускает HP ≤ 0; фактические вызовы для таких юнитов зависят от жизненного цикла движка. Переменная dummyUnit объявлена, но не используется.

### items.rul: анимации, грузы и пена

| Правило | Строка scripts | Событие |
|---|---:|---|
| STR_FPV_BLUE_FLARE_USED | 635 | selectItemSprite |
| STR_FPV_RED_FOAMTHROWER | 711 | damageUnitAmmo |
| STR_FPV_RED_CRANE | 781 | selectItemSprite |
| STR_FPV_BLACK_CRANE | 874 | selectItemSprite |
| STR_FPV_FOAM | 1167 | damageUnitAmmo |
| STR_WEAPON_HEAVY_FLAMETHROWER | 18166 | selectItemSprite |
| STR_WEAPON_HEAVY_FOAMTHROWER_TANK_A | 18337 | damageUnitAmmo |
| STR_UTILITY_FIRE_EXTINGUISHER | 21131 | damageUnitAmmo |
| STR_WEAPON_LAUNCHER_40MM_M583A1_USED | 27321 | selectItemSprite |

**Осветители.** Оба USED-предмета имеют одинаковый код: фаза `(item.id+2)%10`, BIGOB получает прибавку 1..9, FLOOROB — 1..6 от anim_frame с этой фазой. Остальные варианты blit_part индекс не меняют. Их ITEM_TAG_FUSELENGTH=9 обрабатывается глобальным createItem 30, который устанавливает fuse timer. Исчезновение определяется дальнейшей логикой предмета/взрывателя, а не скриптом анимации. В этих двух локальных обработчиках sprite_offset не прибавляется — проверить на нужных способах отображения; автоматически объявлять это ошибкой нельзя.

**Тяжёлый огнемёт.** Анимирует только BIGOB и только если getAmmoItem вернул ненулевой предмет: прибавка `(anim_frame%9)+1`. Затем всегда прибавляет sprite_offset. Наличие боеприпаса здесь не проверяет число оставшихся зарядов; рассинхронизации по item.id нет.

**Краны FPV.** Только для BIGOB: RED требует ALLOW_AMMO_TO_RESPRITE=1, BLACK — 2. Получают правило загруженного боеприпаса и, если NEW_BIGOB_FOR_WEAPON ненулевой, присваивают это значение sprite_index. В файле теги грузов используют диапазон 1800–1828. Это абсолютные значения из int-тега; сам скрипт не выполняет пересчёт смещения ресурсов. На обычной ветке тоже нет прибавления sprite_offset. Нужна проверка соответствия реальным ресурсам и путям отрисовки. Ранний return при замене не отменяет глобальный selectItemSprite, хотя имеющийся глобальный обработчик отсекает предметы, не являющиеся трупами.

**Пена и огнетушитель.** Четыре damageUnitAmmo читают UNIT_IS_EXTINGUISHABLE у брони цели. При значении >0 бросают урон 15..60 (для ручного огнетушителя — 10..50), сравнивают с бронёй выбранного side и вычитают её, если бросок выше брони. Иначе урон устанавливается в 2. Это не общий минимум 2: при превышении брони на 1 результат равен 1. При остатке 3..7 случайно задаются 0..1 ран, при ≥8 — 0..3; иначе 0. Затем перезаписываются to_health и to_wound; остальные компоненты урона сохраняются. Без тега оба выхода остаются прежними.

Этот код сам не вызывает setFire и не гасит юнита напрямую: он задаёт особую уязвимость к пене. Обычные свойства огнетушителя задаются отдельно в ruleset. После него выполняется damageUnit цели с глобальными обработчиками: например, критическое попадание 10 и уменьшение максимального HP 30 способны изменить результат. Поэтому диапазон 15..60 нельзя считать окончательным уроном. damageUnitAmmo привязан к повреждающему предмету; наличие одинакового тела у оружия и отдельного боеприпаса само по себе не означает двойной вызов в одной атаке.

### SCPs.rul: живые аномалии и взаимодействие с глобальными эффектами

Локальные selectUnitSprite у STR_SCP_457_ARMOR_PROTO (1082) и STR_SCP_610_A_ARMOR_UC (1263) повторяют FPV-анимацию: восемь фаз покоя, обычное сложение индекса со смещением при движении/падении, drawingRoutine=4 и constantAnimation=true. Оба правила имеют ARMOR_SPECIAL_ANATOMY=1 и SA_ONLY_TORSO=1.

457 PROTO дополнительно имеет ARMOR_COMMON_ROUTINE=1 и UNIT_IS_EXTINGUISHABLE=1. Первый тег должен исключать особые глобальные анимации; второй включает описанный урон пены. В глобальном selectUnitSprite 6 проверка ARMOR_COMMON_ROUTINE работает, но в offset 4 она стоит до чтения routine (см. наблюдение №3). Таким образом, найденная ранее проблема имеет конкретного потребителя: 457 PROTO может пройти нежелательную обработку индикатора шока, если получит соответствующие теги.

У других вариантов 457 в SCPs.rul присутствуют ARMOR_LIVING_FIRE, регенерация и шанс повторного возгорания; их поведение обеспечивают глобальные скрипты даже без локального scripts. Нельзя автоматически переносить эти свойства на PROTO только по сходству имени: набор тегов у него проверяется отдельно.

### Что добавить к проверке в игре

- Создание нейтралов и противников: рандомизация до сохранения исходных характеристик, исключения UNIT_FIXED_STATS.
- FPV и SCP: покой, движение, падение, индикатор шока и прицеливания поверх локального индекса; особенно ARMOR_COMMON_ROUTINE у 457 PROTO.
- BIGOB/FLOOROB осветителей и смена грузов кранов: проверка sprite_offset и абсолютных индексов 1800–1828.
- Пена: цель с тегом и без него, бросок ниже/равен/выше брони, влияние глобального damageUnit на итоговые HP и раны.
- DUMMY: частота STR_RESPONDERS_CLOSE при низком HP на разных сторонах хода.

Дополнение также основано на статическом анализе. Скрипты и баланс не изменялись; игра не запускалась.
