# Динамические регионы вокруг баз

`baseRegionTemplates` задаёт шаблоны технических регионов. Каждая существующая база получает отдельный экземпляр каждого шаблона. Экземпляры принадлежат сохранению, не добавляются в географический список регионов, не меняют стоимость баз, региональную статистику, финансирование или названия городов на глобусе.

## Шаблон

```yaml
baseRegionTemplates:
  - type: REGION_XCOM_BASE_SURROUNDINGS
    landOnly: true
    maxDistanceKm: 300
    areas:
      - [-4, 4, -3, 3]
    missionZones:
      - # зона 0
        - [-2, 2, -2, 2, -90457]
      - # зона 1
        - [-4, 4, -3, 3, -90457]
```

Это рабочий пример из `bin/standard/OpenSCP/Ruleset/baseRegions.rul`.

- Первые четыре значения — **смещения в градусах** относительно базы: `[lonMin, lonMax, latMin, latMax]`. Отрицательная широта направлена на север. Западнее базы используются отрицательные смещения долготы.
- Минимальная долгота должна быть не больше максимальной, ширина — не больше 360°. Смещения широты ограничены диапазоном от −90° до +90°; при преобразовании абсолютная широта обрезается на полюсах, без отражения в другое полушарие.
- Пятый элемент участка — существующий `globe.textures.id`. Шестой — необязательное название точки. Отрицательные ID поддерживаются без изменений.
- `areas` и `missionZones` обязательны. Зоны должны быть непустыми. Нумерация с нуля, как у обычных регионов. Точки задаются совпадающими границами.
- `landOnly` по умолчанию `true`: при создании объекта миссии проверяется `Globe::insideLand`. Косметический океан исключается; `fakeUnderwater` считается сушей в смысле этой проверки. `false` отключает эту дополнительную проверку, но не отменяет общие ограничения игры на посадку НЛО и требования deployment/terrain.
- `maxDistanceKm` по умолчанию `0`: дополнительного ограничения расстояния нет. Положительное значение ограничивает выбранные точки сферическим расстоянием от базы, с радиусом Земли 6371 км.
- Геометрия остаётся прямоугольной. `maxDistanceKm` отсекает неподходящие точки, но **не расширяет** прямоугольники до полного круга. Один градус долготы возле полюса соответствует меньшему расстоянию, чем на экваторе.
- Для нового режима выбранные точки должны попадать также в `areas`. В обычных статических регионах существующая логика не меняется.
- `missionRegion` для шаблонов запрещён. Географические параметры `cost`, `regionWeight`, `missionWeights` не используются экземплярами.

Переход через Гринвич рассчитывается автоматически: абсолютные `areas` используют обёрнутый диапазон, а `missionZones` — возрастающий диапазон, который может выходить за 360°. До проверки поверхности координата нормализуется.

## Поиск городов рядом с базой

`cityMissionZones` содержит индексы зон, прямоугольники которых используются для поиска существующих городов:

```yaml
baseRegionTemplates:
  - type: REGION_XCOM_BASE_CITY_SURROUNDINGS
    landOnly: true
    maxDistanceKm: 300
    areas: [[-5, 5, -4, 4]]
    cityMissionZones: [3]
    missionZones:
      - [[-2, 2, -2, 2]]
      - [[-4, 4, -3, 3]]
      - [[-5, 5, -4, 4]]
      - [[-5, 5, -4, 4, -1]]
```

Этот дополнительный шаблон включён в `baseRegions.rul`. Для выбора городов миссия должна использовать `spawnZone: 3`, а её `missionScript` — `baseRegionTemplate: REGION_XCOM_BASE_CITY_SURROUNDINGS`. Зоны 0–2 остаются обычными прямоугольниками; номера зон в траекториях НЛО также сохраняют своё значение.

При создании экземпляра движок собирает именованные точки из `missionZones` географических регионов кампании. Технические регионы без `areas` не служат источниками городов. Город должен одновременно попадать в прямоугольник поиска, `areas` и радиус `maxDistanceKm`. Это настроенная в шаблоне досягаемость, она не зависит от радаров или дальности самолётов базы. Повторяющиеся координаты внутри одной зоны учитываются один раз.

В результирующей зоне сохраняются абсолютные координаты и название города. Пятый элемент берётся из первого подходящего прямоугольника поиска: `-1` сохраняет обычное значение этой текстуры для выбора миссии, а сам поиск городов включает именно `cityMissionZones`. Без пятого элемента используется `0`; текстура исходного города не наследуется. Для SCP-457 можно указать `-90457` вместо `-1`, сохранив нужные настройки deployment миссии.

При спавне продолжает действовать `landOnly`: даже именованная точка должна пройти проверку суши, если включён этот параметр. Если подходящих городов нет, экземпляр получает пустую зону, и миссия для неё не создаётся; подмены случайной точкой нет. Явные специальные цели вроде `objectiveOnXcomBase` сохраняют собственную логику выбора цели — их не следует использовать для миссий, которые должны проходить именно в городе.

Найденные города сохраняются вместе с экземпляром региона и не пересчитываются при каждой загрузке. Изменение уже использованного шаблона не обновляет существующие экземпляры: для применения к нынешним базам задайте новый `type` шаблона и используйте его в скрипте. Новый шаблон из примера создаст экземпляры и для существующих баз.

В отладке Ctrl+D у выбранной городской зоны отображается `cities: N`, а вместо сетки возможных случайных координат — точки найденных городов. При выборе конкретного участка отображается название города. Пустая зона показывает `cities: 0`.

## Побеги с привязкой к исходной базе

Для уникального объекта можно сохранить контекст побега между месяцами. Событие регистрирует его только после фактического списания `escapeItem`; неудачный бросок вероятности первичной миссии не удаляет контекст.

```yaml
events:
  - name: STR_EVENT_347_GETAWAY_SUCCESS_TITLE
    invert: true
    everyItemList: [STR_SCP_347_CONTAINED]
    escapeId: SCP_347
    escapeItem: STR_SCP_347_CONTAINED
    escapeRegionTemplate: REGION_SCP_347_ESCAPE_SEARCH
    escapeSearchMonths: 3
    escapeRecoveryItems: [STR_SCP_347_CONTAINED, STR_SCP_347_UNCONTAINED,
                          STR_SCP_347_HIRED, STR_SCP_347_OPTIMIZED]
    # escapeLostEvent: STR_MY_ESCAPE_LOST_EVENT
    adhocMissionScriptTags: [347_initial_escape]
```

`escapeId` обозначает один уникальный объект, а не вид массовых предметов. Для события требуется `invert: true`, ровно один `escapeItem` в фиксированных списках выдачи/списания и существующий шаблон региона. Случайные списки предметов с этим режимом не совмещаются. Для нескольких независимых объектов нужны разные ID и отдельные предметы, позволяющие определить возвращение каждого из них. Источник — база фактического списания; для предмета на припаркованном транспорте это база транспорта. Исходный порядок списания предметов не изменён.

`escapeRecoveryItems` перечисляет альтернативные предметы, наличие любого из которых означает возвращение под контроль. Если список не задан, проверяется `escapeItem`. Учитываются склады, грузы транспортов и предметы в межбазовых переводах. Проверка выполняется каждые 30 игровых минут и перед выбором миссий. Уже созданные миссии автоматически не удаляются. Новые поиски после возвращения прекращаются.

В adhoc-скрипте первичного побега указываются `escapeId: SCP_347` и `baseRegionTemplate: REGION_SCP_347_ESCAPE_SEARCH`, без `targetBaseOdds` и `regionWeights`. Только для событий с контекстом побега adhoc запускается после списания и обработки наград события. Миссия с `objectiveOnXcomBase: true` получает исходную базу. В примере её `spawnZone: 0`, чтобы наличие городов не влияло на первичный побег.

```yaml
missionScripts:
  - type: 347-further-escape
    escapeId: SCP_347
    escapeMinMonths: 1
    baseRegionTemplate: REGION_SCP_347_ESCAPE_SEARCH
    missionWeights:
      0:
        STR_SCP_347_MISSION_FURTHER_ESCAPE: 50
        STR_SCP_347_MISSION_FURTHER_ESCAPE_WILDERNESS: 50
    executionOdds: 80
    startDelay: 1500
```

`escapeMinMonths` — минимальная разница индексов месяцев кампании, по умолчанию `0`. Значение `1` запрещает повторный поиск в месяце побега. Скрипт без зарегистрированного побега не создаст миссию. Все скрипты одного `escapeId` проверяют общую занятость: пока есть незавершённая AlienMission или MissionSite с этим ID, новую миссию не создают. Вероятность, задержка и обычные условия скриптов сохраняют смысл. Если подходящей зоны нет, движок может попробовать другой тип из `missionWeights` обычным алгоритмом; к другой базе поиск не переносится.

Срок `escapeSearchMonths: 3` означает три последующих месяца поиска: при побеге в месяце M разрешены M+1, M+2, M+3; в начале M+4 контекст становится `lost`. Значение `0` оставляет только месяц первичного побега. Это календарные месяцы кампании, а не 90 суток. Успешный или неудачный запуск миссии не продлевает срок. Уже созданную миссию, в том числе ещё ожидающую `startDelay`, можно завершить и после срока. Позднее возвращение объекта меняет состояние на `recovered`.

Необязательный `escapeLostEvent` вызывает существующее событие при переходе в `lost` через обычный механизм `spawnEvent`, с его задержкой и ограничениями. Без него потеря фиксируется в сохранении и логе, отдельного окна нет. Событие не повторяется при загрузке. Оно должно быть уведомлением/последствием потери, а не безусловным повторным запуском поиска.

В сохранении раздел `escapes` хранит исходную базу, снимок региона, месяц побега, срок, список предметов возврата и состояние `searching` / `recovered` / `lost`. Снимок региона удерживается до конца поиска, даже если база уничтожена. Активная миссия также удерживает его после истечения срока. Старые сохранения без контекста не получают его задним числом: он появляется при новом событии списания. Изменения срока в рулсете относятся к новым побегам; уже зарегистрированный срок сохранён в кампании.

Пример SCP-347 подключён в `events.rul`, `missionScripts.rul`, `alienMissions.rul` и `scp347EscapeRegion.rul`. Городской вариант использует зону 3, вариант обычной местности — зону 0. Прямоугольная зона не гарантирует отсутствие населённых пунктов: она выбирает случайную допустимую точку суши.

## Выбор в missionScripts

Полный пример для OpenSCP, который можно добавить отдельным правилом, если требуется дополнительная ежемесячная миссия SCP-457:

```yaml
missionScripts:
  - type: SCP_457_NEAR_XCOM_BASE
    baseRegionTemplate: REGION_XCOM_BASE_SURROUNDINGS
    missionWeights:
      0:
        STR_SCP_457_GENERIC_MISSION_NORMAL: 100
    useTable: false
    firstMonth: 1
    executionOdds: 100
    startDelay: 3000
    researchTriggers:
      STR_COUNCIL_FOUNDED: true
      STR_SCP_457_CAPTURED: false
```

Этот скрипт **не включён автоматически**. Шаблон в `baseRegions.rul` не добавляет миссий к текущему балансу. Чтобы перенаправить существующий скрипт, замените его `regionWeights` на `baseRegionTemplate`, сохранив нужные условия, задержки и веса миссий.

`baseRegionTemplate` требует явного `missionWeights`; его нельзя совмещать с `regionWeights` или ненулевым `targetBaseOdds`. Выбор не использует глобальную таблицу регионов AlienStrategy; `useTable` в этом режиме игнорируется. При отсутствии баз команда ничего не создаёт.

Сначала выбирается тип миссии по существующим весам, затем подходящий экземпляр региона. Для site-миссий базы с подходящими участками выбираются равновероятно, после чего равновероятно выбирается участок. Учитываются существующие проверки активных миссий и `avoidRepeats`; история различает экземпляры регионов разных баз. Для прямоугольников `avoidRepeats` относится к участку целиком, а не к конкретной случайной координате.

`spawnZone` у alien mission и номера зон маршрутов НЛО должны существовать в шаблоне. Пример SCP-457 использует `spawnZone: 0`. Настройка `globe.textures[-90457]` выбирает deployment; приоритет явного deployment/`siteType` остаётся прежним.

При прямом спавне проверка поверхности выполняется повторно в момент создания объекта. На поиск отводится до 1000 попыток. Если подходящей точки нет, объект не создаётся и в журнал пишется причина. Ошибка поиска места НЛО пропускает его появление либо завершает уже летящий НЛО; принудительной посадки в неподходящей точке для этого режима нет. Ограничение расстояния применяется к выбранным точкам, не к каждому промежуточному положению летящего НЛО.

Регионы служат геометрией миссий. Специальные цели стандартных миссий, например нападение на конкретную базу или снабжение базы пришельцев, дополнительно управляются собственными правилами этих миссий. Ответный удар после перехвата НЛО из динамического региона использует обычный географический регион местоположения НЛО и стандартные маршруты retaliation.

## Сохранение и жизненный цикл

- База получает сохраняемый `baseRegionId`, не зависящий от имени и порядка в списке.
- В секции сохранения `baseRegions` хранятся ID экземпляра, шаблон, ID базы, исходная точка, рассчитанные `areas`/`missionZones` и ограничения. `originLon`/`originLat` — внутренние радианы, координаты участков — градусы.
- Динамические регионы восстанавливаются **до** загрузки alien missions. Они доступны через `SavedGame::getMissionRegion`; обычные регионы остаются в `Mod`.
- При загрузке старого сохранения недостающие экземпляры создаются для существующих баз. Синхронизация также выполняется при подтверждении имени базы, открытии геоскейпа и выборе такого скрипта.
- Удалённая база сразу исключается из кандидатов при следующем выборе. Её регион сохраняется, пока на него ссылается активная alien mission. После завершения миссии регион удаляется при следующей синхронизации.
- Изменение координат базы создаёт новый экземпляр; уже начавшиеся миссии продолжают использовать прежнюю геометрию. Это покрывает и начальное размещение первой базы.
- Изменения существующего шаблона не перестраивают уже сохранённую геометрию. Для новой версии геометрии используйте новый `type` шаблона и обновите скрипт. Новые базы получают текущую версию шаблона.
- Старые версии движка не поддерживают миссии, ссылающиеся на динамические регионы. Для открытия таких сохранений нужен движок с этой функцией.

## Просмотр через Ctrl+D

Существующий цикл отладки сохранён: последовательные включения Ctrl+D показывают страны, `areas` регионов и `missionZones` (между включениями режим отключается).

В списке регионов доступны и динамические экземпляры: **имя базы #ID / имя шаблона**. Экземпляр удалённой базы, ещё используемый миссией, обозначается `retained`. Список обновляется при открытии геоскейпа и переключении отладки. Фильтры зон и участков заполняются по реальному количеству записей, без прежних ограничений 20/100.

- В режиме `areas` отображаются границы региона, крестик его центра и окружность `maxDistanceKm`, если ограничение задано.
- В режиме `missionZones` отображаются прямоугольники/точки зон. При выборе конкретного динамического региона также показаны его `areas` и **сетка допустимых точек** с учётом `areas`, радиуса и `landOnly`.
- Сетка — предварительный просмотр, а не полный перечень спавнов: до 17×17 проб на участок. Маленький остров может оказаться между пробами. Специальные ограничения конкретной миссии/НЛО в этой сетке не учитываются.
- Сетка детерминированная и не меняет состояние игрового RNG. Отладочная геометрия видна и при отключённых обычных деталях глобуса.
- В текстовой панели показаны шаблон, ID базы, радиус, `landOnly`, а при выборе участка — координаты и texture ID.

## Проверка

Рабочий код управления экземплярами регионов и контекстами побегов находится в `src/Savegame/BaseRegions.cpp` и `BaseRegions.h`. Класс `BaseRegions` принадлежит `SavedGame`; прежние методы `SavedGame` делегируют ему операции. Геометрия и чтение шаблонов остаются в `RuleRegion`, а загрузка правил — в `Mod`. YAML-ключи `baseRegionTemplates`, `baseRegions` и `escapes`, а также формат сохранений не изменены.

`tests/base-regions.cpp` содержит только автоматические проверки и не входит в исполняемый файл игры. Новый рабочий модуль подключён к сборкам Visual Studio и CMake.

При загрузке мода проверяются как `missionScripts`, так и `adhocScripts`. Если указан `baseRegionTemplate`, запрещён `regionWeights` (включая пустой и унаследованный через `refNode`) и ненулевой `targetBaseOdds`. Ошибка останавливает загрузку мода и содержит ID скрипта, имя шаблона, конфликтующие поля и инструкцию по исправлению. Явный `targetBaseOdds: 0` разрешён. Проверка выполняется после объединения определений, поэтому переопределить унаследованный `targetBaseOdds` нулём допустимо. Без `baseRegionTemplate` обычные географические скрипты сохраняют прежнее поведение.

На Windows с Visual Studio C++ tools:

```powershell
powershell -ExecutionPolicy Bypass -File tests/run-base-regions.ps1
```

Скрипт собирает Win32 Release и запускает отдельный исполняемый файл регрессионных проверок. Проверяются переход через Гринвич, полюса, полный диапазон долгот, ограничение расстояния, отказ при неподходящей поверхности, сериализация, независимость баз, старые базы без ID, удаление базы при активной миссии и изменение первоначального положения базы. Тесты поверхности используют предикат поверхности, а не игровые графические ресурсы.

Для ручной игровой проверки: разместить базу у Гринвича или на побережье, включить пример mission script, дождаться миссии, сохранить/загрузить игру и проверить положение объекта. Отдельно проверить миссию с несколькими волнами НЛО и удаление базы между волнами.
